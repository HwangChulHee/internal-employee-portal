# 한글 성명 매핑

## 문제

사내 DB는 이름이 하나(`김민준`), 외부 API는 `firstName` / `lastName` 둘을 요구한다.
하나를 둘로 분리해야 하는데, 세 가지 난점이 있다.

### 1. 순서가 반대다

```
John Doe          김민준
└┬─┘ └┬┘          └┬┘└─┬─┘
first last         성   이름
                  last first
```

영어권은 **first = 개인 이름**, **last = 가족 이름(성)** 으로 의미가 정해져 있다.
한국 이름은 성이 앞에 오므로 `김민준` → `lastName: "김"`, `firstName: "민준"`이 된다.

**"앞 = first"가 아니다.** 직관과 반대라 자주 틀리는 지점이다.

### 2. 절단 위치가 모호하다

| 이름 | 성 | 이름 | 비고 |
|---|---|---|---|
| 김민준 | 김 | 민준 | 단성, 문제 없음 |
| 선우재덕 | 선우 | 재덕 | 복성 목록으로 처리 가능 |
| **남궁민** | 남 or 남궁 | 궁민 or 민 | **판별 불가** |
| **황보나** | 황 or 황보 | 보나 or 나 | **판별 불가** |

복성(두 글자 성)은 남궁·황보·제갈·선우·독고·사공·서문·동방 등 10개 남짓이다.
목록으로 대부분 처리할 수 있으나, **3글자 이름은 목록이 있어도 판별할 수 없다.**

### 3. 로마자 표기가 개인마다 다르다

| 성 | 표준 표기 | 실제 사용 |
|---|---|---|
| 김 | Gim | Kim |
| 이 | I | Lee, Yi, Rhee |
| 박 | Bak | Park |

여권에 어떻게 기재되어 있는지는 본인만 안다. 자동 변환으로는 정확할 수 없다.

---

## 실측으로 확인한 사실

설계 전 외부 API를 직접 호출해 확인했다.

**1. 이름 형식 검증이 없다**

```
firstName: "민준", lastName: "김"  →  201 Created
```

한글을 그대로 보내도 성공한다. **로마자 변환은 강제 사항이 아니라 선택이다.**

**2. 응답 결과가 무작위다**

동일한 요청에 `clear` / `flagged` / `pending`이 무작위로 반환된다.
따라서 **"이름이 틀려서 조회에 실패했다"는 신호가 존재하지 않는다.**

**3. `dateOfBirth`가 실질적 식별 키다**

이름만으로는 동명이인을 구분할 수 없다. 생년월일이 매칭의 핵심이므로,
이름 분리 오류의 실질적 영향은 제한적이다.

## 결정

| 항목 | 결정 | 근거 |
|---|---|---|
| DB 저장 | 통이름 컬럼 하나 (`name`) | 요구사항이 성/이름 분리를 요구하지 않음 |
| 변환 위치 | 백엔드 `external/name_mapper.py` | 프론트는 외부 API를 호출하지 않음 |
| 로마자 변환 | 하지 않음 | 정확할 수 없고, API가 한글을 수용함을 확인 |
| 기본 분리 규칙 | 성 1글자 | 단성이 압도적으로 많음 |
| 복성 후보 | 조회 시점에 관리자가 확정 | 시스템이 추측하지 않음 |
| 확정값 저장 | `employees`가 아닌 `background_checks`에 전송값 기록 | 조회 빈도가 낮아 재사용 가치가 작음 |
| 수신 시 | API 응답의 이름 필드 무시, 내 DB의 `name` 표시 | 사내 화면에 외국식 표기는 부자연스러움 |

## 처리 흐름

```
관리자가 Background Check 요청
    ↓
백엔드가 모호성 판별
  (앞 2글자가 복성 목록에 있고 길이가 3 이상인가)
    ↓
모호하면 → "성이 '남'입니까, '남궁'입니까?" 확인 요청
    ↓
선택된 값으로 외부 API 호출
    ↓
background_checks에 실제 전송한 first/last 기록
```

### 변환 함수

```python
COMPOUND_SURNAMES = {"남궁", "황보", "제갈", "선우", "독고", "사공", "서문", "동방"}


def is_ambiguous(name: str) -> bool:
    """복성 여부를 규칙만으로 판별할 수 없는 이름인가."""
    return len(name) >= 3 and name[:2] in COMPOUND_SURNAMES


def to_external_name(name: str, surname: str | None = None) -> tuple[str, str]:
    """사내 한글 성명을 외부 API 형식으로 변환한다.

    Returns:
        (first_name, last_name) — first가 이름, last가 성이다.
    """
    if surname:
        if not name.startswith(surname):
            raise ValueError("성은 이름의 앞부분과 일치해야 합니다")
    elif len(name) >= 3 and name[:2] in COMPOUND_SURNAMES:
        surname = name[:2]
    else:
        surname = name[:1]

    given = name[len(surname):]
    return given, surname
```

반환 순서에 주의한다. **first가 이름, last가 성이다.**

`surname` 인자에 대한 접두사 검증이 필요하다.
검증이 없으면 `남궁민`에 `김`을 지정하는 경우 `given`이 잘못 잘린다.

## 배제한 대안들

### 여러 조합으로 반복 조회

`남궁민`을 "남/궁민"과 "남궁/민" 두 번 조회하는 방안.

**배제 근거:**

- **실패 신호가 없다.** `flagged`는 "추가 검토 필요"일 뿐 이름 오류를 뜻하지 않는다
- 두 결과가 모두 반환되면 어느 쪽이 정확한지 **검증할 방법이 없다**
- **타인의 기록이 매칭될 위험**이 있다. 조회 실패보다 나쁜 결과다
- 실제 서비스라면 건당 과금이 발생하고, 중복 이력이 누적된다

무엇보다 **모호함을 시스템이 판별할 수 있다.** 알 수 있는데 추측할 이유가 없다.

### 로마자 변환

API가 한글을 수용하므로 변환할 이유가 없다.
변환하더라도 개인의 여권 표기를 알 수 없어 정확성을 보장할 수 없다.

### 성·이름 분리 저장

요구사항이 성/이름 분리를 요구하지 않으므로 내부 모델을 나누지 않는다.
외부 시스템 하나의 형식에 맞춰 내부 모델을 바꾸면, 다음 외부 시스템이 추가될 때 다시 바꿔야 한다.

### `employees`에 확정값 컬럼 추가

신원조회는 직원당 1~3회 수준이므로 재사용 가치가 작다.
전송값은 `background_checks`에 기록되므로 추적도 가능하다.

### 개명 시 재검증

발생 확률이 낮고 대응 비용이 크다. 다루지 않는다.

## 문제의 본질

이름은 표면이고, 실제 주제는 **"내부 도메인 모델과 외부 도메인 모델이 다를 때 어떻게 맞출 것인가"** 이다.

같은 계열의 문제가 실무에 널려 있다.

| 내부 | 외부 | 문제 |
|---|---|---|
| 통이름 | first / last | 분리 규칙이 모호 |
| 주소 한 줄 | street / city / state / zip | 국내 주소 체계에 state가 없음 |
| `010-1234-5678` | E.164 (`+821012345678`) | 국가코드, 앞자리 0 처리 |

전부 영어권 데이터 모델을 전제한 외부 시스템과 연동할 때 발생한다.
손실 없는 변환이 불가능하므로 **어디서 정보를 잃고 그 손실을 어떻게 관리할지**를 결정하는 것이 설계다.

적용한 원칙:

1. **내부 모델을 오염시키지 않는다** — 외부가 요구한다고 DB를 분리하지 않는다
2. **경계에 변환 계층을 둔다** — 변환 규칙이 한곳에 모인다
3. **손실 있는 변환에는 사람이 개입할 여지를 남긴다** — 자동화하되 확인 가능하게
