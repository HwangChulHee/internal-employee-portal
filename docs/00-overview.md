# 개요와 문제 분해

## 무엇을 만드는가

사내 직원 관리 웹 애플리케이션. 직원용 UI와 관리자용 UI가 분리되어 있다.

| 사용자 | 기능 |
|---|---|
| 직원 | 본인 인적사항 조회·수정, 비밀번호 변경 |
| 관리자 | 직원 계정 생성(사번 자동 발급), 전체 목록·상세 조회, 정보 수정, 퇴사 처리, 비밀번호 초기화, 신원조회 요청·결과 열람 |

기본 골격은 CRUD이지만, 요구사항에 세 가지 난점이 포함되어 있다.

---

## 세 가지 난점

### 1. 불안정한 외부 API

외부 Background Check API를 연동해야 한다. 실제로 호출해 확인한 특성:

- 요청이 `pending`으로 접수될 수도, 즉시 완료될 수도 있다
- 완료까지 약 10초 소요
- 응답 결과가 무작위다 (목 API)
- `503` 응답에 `retryAfter` 값이 포함된다
- 완료 전에는 세부 결과 필드가 `null`이다

요구사항에 "지연·오류가 발생할 수 있으니 실서비스 수준으로 견고하게"라고 명시되어 있다.
정상 경로만 구현해서는 안 된다는 뜻이다.

### 2. 이름 형식 불일치

사내 직원 데이터는 한글 통성명 하나(`김민준`)인데, 외부 API는 `firstName` / `lastName`을 요구한다.
요구사항이 이 매핑을 "과제의 일부"라고 명시하고 있다.

실측 결과 API에 형식 검증이 없어 한글을 그대로 보내도 통과한다.
즉 로마자 변환은 강제 사항이 아니라 설계 판단의 영역이다.

### 3. 퇴사 즉시 차단

"퇴사 처리되었을 때 즉시 차단"이 요구사항이다.
이 **"즉시"** 때문에 인증 방식 선택 자체가 종속된다. 상세는 `02-auth-design.md` 참조.

## 다루지 않기로 한 것

**부하 테스트 / 성능 최적화**

- 요구사항에 성능 관련 언급이 없다
- 200명 규모 사내 시스템에 트래픽 병목이 존재하지 않는다
- 외부 API는 출제자가 운영하는 AWS 리소스이므로 대량 호출은 부적절하다

요구사항이 말하는 "견고함"은 처리량이 아니라 **실패 상황을 견디는 능력**으로 해석했다.

**캐싱 전략, 샤딩, 마이크로서비스 분리, 오케스트레이션**

현재 규모에서 정당화할 근거가 없다.

## 전반적 판단 기준

설계 결정 시 일관되게 적용한 기준은 다음과 같다.

> **발생 확률 × 대응 비용 × 발생 시 피해**를 함께 본다.

이 기준으로 배제한 것들:

| 항목 | 판단 |
|---|---|
| Redis 세션 저장소 | 서버 1대, 200명 규모에 불필요 |
| 저장소 추상화 계층 | 교체 시나리오가 실재하지 않음 |
| 개명 시 이름 매핑 재검증 | 확률 낮고 대응 비용 큼 |
| DB 선점 패턴 / 부분 유니크 인덱스 | 동시 요청 확률이 극히 낮고, 발생해도 이력 중복 정도의 영향 |

채택한 것들:

| 항목 | 판단 |
|---|---|
| 외부 API 클라이언트 추상화 | 실패 재현이 지금 당장 필요 |
| 외부 전송값 기록 | 비용 거의 0, 없으면 추적 불가 |
| 매 요청 재직 상태 확인 | 어차피 사용자 조회가 필요하므로 추가 비용 없음 |

같은 "추상화"라도 하나는 투기이고 하나는 현재 필요다. 그 구분이 판단의 핵심이었다.
