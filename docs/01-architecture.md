# 아키텍처

## 3계층 구조

```
┌─────────────────────────────────────────┐
│ 1. 브라우저 (신뢰 불가)                  │
│    직원 화면 / 관리자 화면               │
│    → 화면을 숨기는 것은 보안이 아니다     │
└──────────────────┬──────────────────────┘
                   │
┌──────────────────▼──────────────────────┐
│ 2. 백엔드 (신뢰 경계)                    │
│    인증·인가 → 직원 CRUD                 │
│    중계 계층 → DB                        │
└──────────────────┬──────────────────────┘
                   │ firstName / lastName
┌──────────────────▼──────────────────────┐
│ 3. 외부 Background Check API (통제 불가) │
│    pending · 500 · 503 발생              │
└─────────────────────────────────────────┘
```

각 계층의 **신뢰 성격이 다르다**는 것이 이 구조의 핵심이다.

| 계층 | 신뢰도 | 이유 |
|---|---|---|
| 브라우저 | 신뢰 불가 | 사용자가 코드를 수정할 수 있다 |
| 백엔드 | 방어선 | 모든 검증이 여기서 일어난다 |
| 외부 API | 불안정 | 악의가 아니라 지연·장애가 문제다 |

---

## 프론트엔드가 외부 API를 직접 호출하지 않는 이유

기술적으로는 가능하지만 네 가지 문제가 있다.

**1. 권한 검증 불가**
브라우저에서 직접 호출하면 누구나 임의의 직원에 대한 신원조회를 실행할 수 있다.

**2. 민감정보 노출**
개발자 도구 네트워크 탭에 범죄이력, 신용등급, 생년월일이 그대로 노출된다.
요구사항의 "민감정보는 권한에 맞게 다뤄 주세요"에 위배된다.

**3. CORS**
외부 API가 CORS 헤더를 허용한다는 보장이 없다. 허용하지 않으면 브라우저에서 호출 자체가 실패한다.

**4. 재시도·폴링 유실**
재시도와 폴링 로직을 브라우저에 두면 사용자가 탭을 닫는 순간 중단된다.

어차피 관리자 권한 검증을 서버에서 해야 하므로, 중계 구조가 자연스럽다.

---

## 조회 결과를 DB에 저장하는 이유

요구사항에 명시되어 있지는 않지만 저장한다.

- 외부 API가 장애 상태여도 과거 결과는 조회할 수 있어야 한다
- 관리자가 화면에 들어올 때마다 재요청하면 불필요한 비용과 부하가 발생한다
- 사내 `employeeId`와 외부 `checkId`를 연결하는 기록이 필요하다

**외부 API가 진실의 원천이고, 우리 DB는 사본이다.** 이 관계를 전제로 설계한다.
로컬 상태가 `pending`인 경우 상세 조회 시점에 외부에 재확인하여 동기화한다.

## 백엔드 디렉토리 구조

```
backend/app/
├── main.py          FastAPI 앱, 미들웨어
├── config.py        환경변수 (pydantic-settings)
├── database.py      async 엔진, 세션 팩토리, Base
│
├── models/          SQLAlchemy 모델 (DB 테이블)
├── schemas/         Pydantic 스키마 (API 입출력)
├── api/             라우터
├── core/            인증·인가 의존성, 보안 유틸
├── services/        비즈니스 로직
└── external/        외부 API 클라이언트, 이름 변환
```

### 설계 의도

**`models/`와 `schemas/` 분리**

DB 테이블 구조와 API 입출력 형태는 다르다.
필드 수준 인가가 `schemas/`에서 이뤄진다 — 직원용 수정 스키마에는 `role` 필드가 아예 존재하지 않는다.

**`external/`을 별도로 분리**

외부 API와 닿는 코드를 한곳에 모은다. 중계 클라이언트, 이름 변환, 가짜 클라이언트가 여기 들어간다.
`services/`는 이 인터페이스만 호출하므로 나머지 코드는 외부 API의 존재를 몰라도 된다.

이름 변환(`name_mapper.py`)이 여기 위치하는 것이 중요하다.
"이름 분리는 외부 경계에서만 일어난다"는 결정이 디렉토리 위치로 표현된다.

**`core/deps.py`**

`get_current_employee`, `require_admin`, `require_self_or_admin`을 모은다.
FastAPI의 `Depends` 체인으로 인증과 인가를 분리한다.

## 프론트엔드 구조

```
frontend/src/
├── api/          API 호출 함수
├── pages/        화면
├── components/   공용 컴포넌트
└── hooks/        커스텀 훅
```

상태관리 라이브러리는 도입하지 않는다.
화면이 6개 수준이고 대부분이 서버 상태라 `useState`와 fetch로 충분하다.

### 라우팅

| 경로 | 접근 권한 |
|---|---|
| `/login` | 누구나 |
| `/me` | 재직 중인 직원 |
| `/admin/employees` | 관리자 |
| `/admin/employees/new` | 관리자 |
| `/admin/employees/:id` | 관리자 |

프론트엔드 라우팅 가드는 UX를 위한 것이며 보안 수단이 아니다.
모든 접근 제어는 백엔드에서 다시 검증한다.

## 개발·배포 환경의 출처(origin) 구성

세션 쿠키를 사용하므로 same-origin 구성이 유리하다.

**개발 환경**: Vite 프록시로 `/api`를 백엔드(8000)로 전달한다.
브라우저 입장에서는 같은 출처이므로 CORS와 `SameSite` 문제가 발생하지 않는다.

**배포 환경**: FastAPI가 React 빌드 결과물을 정적 파일로 서빙한다.
단일 서버·단일 도메인이 되어 `samesite="lax"`를 그대로 사용할 수 있다.

프론트와 백엔드를 다른 도메인에 배포하면 `samesite="none"`이 필요해지고,
이는 CSRF 방어를 약화시켜 별도 대책이 필요해진다. 이를 피하기 위한 구성이다.
